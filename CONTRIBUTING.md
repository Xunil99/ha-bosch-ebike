# Contributing to ha-bosch-ebike

Thanks for taking the time to contribute! This project is maintained by one
person in their spare time, so every bug report, translation, and pull
request genuinely helps.

By participating, you're expected to follow the
[Code of Conduct](CODE_OF_CONDUCT.md).

## This repo covers two different things

- **The Home Assistant integration** (`custom_components/ha_bosch_ebike/`,
  plus its Lovelace cards in `www/`) - Python and JavaScript, talks to
  Bosch's cloud API.
- **ESPHome firmware** (`esphome/`) for the optional Bluetooth bridges
  (Live Data Interface bridge, Charge Limiter, Cockpit display) - C++/YAML.

They're independent; a contribution usually only touches one of the two.

## Reporting a bug

Please use the **Bug report** issue template - it asks for the handful of
details (Home Assistant version, integration version, which Bosch system
you have: Smart System or eBike System 2, logs) that are almost always
needed to reproduce anything, so starting with them saves a round trip.

Before opening a new issue, a quick search of existing (including closed)
issues is appreciated - several recurring topics (Bosch drive-unit ride-mode
codes, in particular) already have a running thread where a new code can
just be added as a comment.

Found a security-relevant issue (leaked credentials, a way to access
another account's data, and similar)? Please **don't** open a public issue -
see [SECURITY.md](SECURITY.md) instead.

## Suggesting a feature

Use the **Feature request** issue template. A short description of the
problem you're trying to solve is more useful than a fully-specified
solution - there's often already a piece of data available (from the Bosch
API or the LDI bridge) that solves it more simply than expected, or a
similar card/sensor already exists that could be extended instead of adding
something new.

## Contributing code

1. Fork the repository and create a branch off `main`.
2. Make your change, following the style already used in the surrounding
   code (this project leans toward explaining *why* a piece of code exists
   in comments, not just what it does - future readers, including the
   maintainer six months later, benefit from that).
3. Run the relevant checks locally before opening a pull request (see
   below).
4. Open a pull request against `main` using the PR template. Link the
   issue it addresses, if any.

### Running the checks (Python / integration)

The Python test suite is dependency-free - every file under `tests/` is a
plain script, no `pytest` or virtualenv needed:

```bash
for f in tests/test_*.py; do python3 "$f" || break; done
```

If you touched anything Bosch-API-shaped (parsing, sensors, the
coordinator), add or extend a test for it - most files under `tests/` are a
good example of the style: build a fixture that matches a real API
response, assert on the parsed result, and comment on any real-world quirk
the fixture is there to catch.

### Running the checks (Lovelace cards / JavaScript)

The card bundle lives in `custom_components/ha_bosch_ebike/www/`. If you
add or change any user-visible text, it needs to be added to **all seven**
supported languages (`bosch-ebike-i18n.js`: en, de, nl, fr, it, es, cs) in
the same order, then validated:

```bash
node tests/check_card_i18n.mjs
```

This checks key parity, ordering, and that placeholder-taking strings
(functions) still interpolate all their arguments in every language - it's
strict on purpose, since a mismatch here silently breaks the card for
whichever language it hits.

Contributing a **new** language is very welcome - open an issue first so
translation terminology (a lot of domain terms like ride mode names are
deliberately left untranslated to match the Bosch Flow app) can be agreed
on before a big PR lands.

### Running the checks (ESPHome firmware)

```bash
esphome compile esphome/factory-c3.yaml
```

(or whichever `.yaml` you touched - `factory.yaml`, `factory-dual.yaml`,
`factory-charge-limiter.yaml`, `display-jc4827w543.yaml`). CI compile-checks
every firmware variant on every push; a change that doesn't compile for all
of them will fail there even if your own board builds fine.

### Documentation

User-facing changes (new card, new config option, new sensor) should come
with a matching addition to `README.md`. This repo maintains German and
English as the two primary languages for prose documentation (with several
community-contributed additional language versions, `README.*.md`) - adding
just the German+English section is fine, other languages can follow later
without blocking a PR.

### Commit messages

Plain, descriptive commit messages are fine - no enforced format. Please
don't include a `Co-Authored-By` trailer generated by an AI coding tool;
attribute the commit to yourself.

## What happens after you open a PR

This is a one-person project, so review can take a few days depending on
free time. CI (tests, i18n check, firmware compile, HACS/hassfest
validation) has to pass before anything gets merged. Feedback is meant as
collaborative, not gatekeeping - see the Code of Conduct for the tone this
project aims for either way.
